部署方式｜雲端 API

雲端：最強的腦，但要想清楚資料去哪

優點

  • 能力最強：長上下文、多步驟推理、工具呼叫
  • 上線快：不用買硬體、不用維運
  • 按用量付費，模型持續升級

缺點與限制

  • 資料離開公司，需靠合約與設定控管
  • 用量大時長期成本高、費用難預估
  • 依賴網路與供應商，改版會影響輸出

適合場景

  • 複雜推理與規劃、文件撰寫與彙整
  • 不敏感或已去識別化的資料
  • PoC 驗證、用量還不確定的初期

評估事項

  • 資料條款：是否用於訓練、保留多久、可否指定區域
  • 成本試算：月 token 量 × 單價
  • 速率限制、SLA、斷網時的備援
  • 保留切換模型的介面，避免綁定單一廠商
部署方式｜地端部署

地端：資料不出廠，但能力有天花板

優點

  • 資料不出廠，符合法規與客戶要求
  • 成本可預期，用量越大越划算
  • 可離線運作，可針對領域微調

缺點與限制

  • 硬體門檻：顯示卡記憶體決定模型大小
  • 開源中小模型的複雜推理明顯較弱
  • 需要維運人力：更新、監控、資安

適合場景

  • 機敏資料的分類、抽取、摘要、問答
  • 高頻、格式固定的小任務
  • 產線離線或網路受限的環境

評估事項

  • 記憶體估算：參數量 × 每參數 bytes + KV cache
  • 例：32B 模型 Q4 量化，權重約 18–20 GB
  • 授權條款：能否商用
  • 地端不等於安全：權限控管與稽核一樣要做
部署方式｜混合式架構

混合式：依資料與任務分流，不是兩邊都用

模式 A　雲端當大腦，地端當手腳

  1. 雲端
  2. 只看 schema 與任務描述，不碰原始資料
  3. 雲端
  4. 產出執行計畫、SQL、限制式
  5. 地端
  6. 在真實資料上執行，結果留在公司內

例：ERP 成本分析、插單評估與排程

模式 B　地端當守門員

  1. 地端
  2. 資料分級、遮罩、去識別化
  3. 雲端
  4. 對處理過的內容做推理與彙整
  5. 地端
  6. 把代碼還原成真實名稱與數字

例：客訴分析、合約與報告摘要

適合場景

  • 同時有機敏資料與複雜任務
  • 大多數製造業都落在這裡

代價

  • 兩套系統都要維運
  • 路由邏輯與資料邊界要設計

評估事項

  • 哪些欄位可以上雲，要先劃清
  • 斷網時地端能否降級運作

模型｜回到問題

Benchmark 是參考，選哪個、換不換，回到要解決的問題

選型流程

  1. 定義業務問題與成功標準
  2. 用 benchmark 篩出候選模型
  3. 用自己的資料建立評測集
  4. 實測品質、每任務成本、回應時間
  5. 決定導入，或維持現狀

新模型出來，要不要換？

  • 現行模型已經達標了嗎？
  • 在自己的評測集上，真的有進步嗎？
  • 每任務成本與回應時間怎麼變？
  • 遷移成本：prompt 調整、輸出格式、回歸測試

合約審閱不需要 FrontierMath 滿分，產線排查也不需要 ARC-AGI-3 滿分

模型｜地端模型

對話任務：用 Arena 盲測回答風格

過去的 Chatbot Arena（LMArena），2026 年 1 月更名為 Arena

運作方式

  1. 輸入同一個問題
  2. 兩個匿名模型各自回答
  3. 投票選出比較好的回答
  4. 揭曉模型身分，累積成排行榜
arena.ai ↗

怎麼用

  • 指定兩個候選模型並排比較
  • 用自己的業務問題實測，選出喜歡的回答風格

要注意

  • 排名反映大眾偏好，不等於你的任務表現
  • 投票者偏好較長、排版漂亮的回答
  • 研究指出投票可能被操弄

      Takeaways｜企業學員

      帶回公司的四個決策原則

      1架構選型
      • 用「資料敏感度 × 任務複雜度」盤點 use case，多數企業會走向混合式
      • 先訂資料邊界：哪些欄位可以上雲
      • LLM 負責理解與表達，計算交給演算法，決策留給人
      2模型
      • Benchmark 只用來篩選，最後用自家資料建立評測集
      • 雲端選「型號 × 推理強度」，用每任務成本估預算
      • 地端先確認授權能否商用、模型來源是否符合客戶要求
      3硬體
      • 記憶體放得下只是門票，多人使用要看頻寬與算力
      • 需求 = 權重＋KV cache＋開銷，再留 20% 餘裕
      • 價格波動大：先用雲端驗證價值，再決定採購
      4推論
      • 試用選 Ollama、LM Studio；全廠服務選 vLLM＋Linux
      • 統一用 OpenAI 相容 API，保留雲地切換彈性
      • Windows、AMD 環境限制多，採購前先確認軟體支援
      Takeaways｜在學學生

      帶得走的四項能力

      1架構選型
      • 會用「資料 × 任務」矩陣分析問題，說得出選型理由
      • 知道 LLM 的能力邊界：最佳化、精確計算交給演算法
      • 畫得出雲地分工的架構圖與資料流向
      2模型
      • 讀得懂 Model Card 與 benchmark，分辨飽和指標與內部測試
      • 會用 Hugging Face 找模型、看授權、挑量化版本
      • 用 Groq 串接開源模型，熟悉 OpenAI 相容 API
      3硬體
      • 算得出記憶體需求：參數量、量化、KV cache
      • 知道頻寬決定產生速度、算力決定讀取速度
      • 不必先買硬體：筆電跑 4B～8B，或用雲端 API
      4推論
      • 在自己電腦裝 Ollama 或 LM Studio，實測 tokens/秒
      • 比較不同量化、GPU 比例下的速度並記錄
      • 進階：在 Linux 上用 vLLM 架一個多人服務
